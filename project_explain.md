# sofi-mail — что это за проект и как он устроен

Понятное описание проекта и его компонентов.

Инструкция по локальному запуску для проверки связки с Open WebUI вынесена
отдельно — см. `tests/stand/README.md`.

---

## 1. Идея одной фразой

**Чат с локальной LLM через обычную электронную почту вместо веб-интерфейса.**

За моделью закреплён отдельный почтовый ящик Exchange. Пользователь пишет туда
письмо — сервис забирает его, спрашивает модель и присылает ответ обычным
письмом. Ответ пользователя (Reply) продолжает ту же переписку: сервис помнит
контекст треда.

Зачем так: первые лица компании читают почту в Outlook и не ходят в веб-чаты.
Почта — интерфейс, который у них уже есть.

```
Пользователь                     sofi-mail                    Open WebUI + vLLM
    │                                │                                │
    │ письмо «Вопрос»                │                                │
    ├───────────► Exchange ──────────┤ опрос ящика (EWS, каждые 20 c) │
    │                                │                                │
    │                          разбор письма                          │
    │                          поиск/создание сессии                  │
    │                          разбор вложений                        │
    │                                ├──── история + вопрос ─────────►│
    │                                │◄─────────── ответ ─────────────┤
    │                          запись в SQLite                        │
    │ письмо «Re: Вопрос»            │                                │
    │◄─────────── Exchange ◄─────────┤                                │
```

## 2. Ключевое архитектурное решение

**Модель настраивается не в проекте, а в Open WebUI.**

Системный промпт, температура, потолок ответа, окно контекста, базы знаний
и фильтры живут на модели `sofi-mail` в рабочем пространстве Open WebUI
(Workspace → Models). В коде проекта их нет вовсе.

Демон знает о модели ровно три вещи: **адрес** (`LLM_BASE_URL`),
**ключ** (`LLM_API_KEY`) и **идентификатор** (`LLM_MODEL`). В теле запроса
уходят только `model`, `messages` и, если были вложения, `files`.

Почему так: одно место правки вместо двух. Поменять промпт — зайти в веб-интерфейс,
а не пересобирать образ и не ходить на сервер. И наоборот: если бы демон слал
`temperature` в запросе, он бы молча перекрыл настройку модели, и ответ
разошёлся бы с тем, что администратор видит в интерфейсе.

## 3. Внешние системы (в проекте их нет, они рядом)

| Система | Роль | Как ходим |
|---|---|---|
| **Microsoft Exchange** | почтовый ящик модели | EWS (Exchange Web Services) — тот же протокол, что у Outlook |
| **Open WebUI** | шлюз к модели, хранилище файлов, вся настройка модели | HTTPS, OpenAI-совместимый API + свой файловый REST |
| **vLLM / Qwen-72B** | собственно инференс | напрямую **не** трогаем — только через Open WebUI |

Ни Open WebUI, ни сервер инференса в `docker-compose.yml` не входят: это
отдельные машины, контейнер ходит к ним по сети как обычный клиент.

## 5. Как обрабатывается одно письмо

Пошагово, `pipeline.process_email`:

1. **Разбор** (`email_parser.parse_email`) — из MIME достаются отправитель,
   тема, `Message-ID`, предки треда, тело (HTML при необходимости
   разворачивается в текст), вложения.

2. **Фильтры отказа.** Молча пропускаем: автоответы, письма самому себе, петли
   (по своему заголовку `X-Sofi`), отправителей не из `ALLOWED_SENDERS`.
   Именно молча — ответ подтвердил бы спамеру, что ящик живой.

3. **Заявка в журнале** (`storage.claim_message`) — атомарная отметка «письмо
   взято в работу» **до** генерации. Перезапуск демона в середине обработки
   не приведёт ко второму ответу.

4. **Лимит писем в час** (`RATE_LIMIT_PER_HOUR`) — при превышении пользователю
   уходит уведомление, а не ответ модели.

5. **Поиск сессии.** Сначала по заголовкам треда (`In-Reply-To`/`References`),
   потом — опционально — по нормализованной теме (`THREAD_BY_SUBJECT`).
   Не нашлось — создаётся новая сессия.

6. **Вложения.** Документ разбирается локально (`unstructured` + `pdfminer`),
   извлечённый текст уезжает файлом в Open WebUI, `file_id` пишется в базу.
   До `ATTACHMENT_FULL_CONTEXT_PAGES` страниц документ подаётся целиком
   (`context=full`), дальше — фокусированным поиском плюс оглавление в тексте
   запроса.

7. **Запрос к модели.** История сессии + текущее письмо, обрезанные под
   `MAX_CONTEXT_CHARS`. Текущее письмо не выбрасывается никогда. Три попытки
   при сбое.

8. **Отправка ответа.** `reply_builder` собирает MIME с заголовками треда;
   `Message-ID` генерируется заранее, чтобы ответ пользователя нашёл свою сессию.

9. **Запись в историю.** Ответ модели пишется в базу **только после успешной
   отправки** — иначе ручной повтор породил бы второй ответ на тот же вопрос.

10. **Отметка «прочитано»** в Exchange. При ошибке письмо остаётся
    непрочитанным и возвращается в очередь командой `retry`.

## 6. Данные: что где лежит

**SQLite** (`data/sessions.db`, в контейнере — именованный том), 4 таблицы:

| Таблица | Что хранит |
|---|---|
| `sessions` | «чат» = тред писем с одним адресатом: тема, собеседник, даты |
| `messages` | реплики сессии (`user`/`assistant`), привязка к `Message-ID` письма |
| `processed` | журнал писем — гарантия «ровно один ответ на письмо» |
| `session_files` | вложения, загруженные в Open WebUI: `file_id`, страницы, оглавление |

Каталог базы принудительно приводится к `0700`, файл — к `0600`, на каждом
подключении. В базе лежит переписка целиком, права по умолчанию отдали бы её
любому пользователю сервера.

**Open WebUI** — единственное место, где данные переписки оказываются на чужой
стороне: туда уезжает извлечённый текст вложений. У него свой срок хранения
(`ATTACHMENT_RETENTION_DAYS`, по умолчанию 30 дней) и своя уборка. Чаты
в Open WebUI демон **не создаёт**: под общей сервисной учёткой они сложились бы
в один общий журнал переписки всех пользователей.

## 7. Режим защиты данных

Переписка первых лиц — это персональные данные, и код это учитывает явно:

- **Телеметрия выключена принудительно** в `config.py` до первого импорта
  библиотек: LangSmith (`LANGCHAIN_TRACING_V2` и родня) и `unstructured`
  (`DO_NOT_TRACK`). Значения выставляются жёстко — перекрыть их из окружения нельзя.
- **HTTPS обязателен** до Open WebUI. С `http`-адресом демон не стартует:
  в запросе уходит полный текст письма. Исключение оформляется явно —
  `LLM_ALLOW_INSECURE=true`.
- **Логи маскируются**: адрес → `i***@company.ru`, тема письма не пишется вовсе.
  `LOG_PII=true` — только на время разбора конкретной проблемы.
- **Срок хранения** (`RETENTION_DAYS=90`) и **удаление по требованию**
  (`forget --session N` / `--address A`), включая снятие файлов в Open WebUI.
- **`STORE_RAW_BODY=false`** по умолчанию: тело письма с цитатой содержит
  реплики третьих лиц, которые сервису не писали.
- **Доменные записи в whitelist запрещены** по умолчанию: `@company.ru`
  пустил бы любого сотрудника, включая того, кому переслали чужой тред.
- **Контейнер**: read-only корневая ФС, все capabilities сброшены,
  `no-new-privileges`, `.env` монтируется файлом (не `env_file` — иначе пароль
  виден в `docker inspect`).

## Как запустить и проверить

**Боевая выкладка** — в `README.md`: сборка образа, настройка `.env`, запуск
`docker compose`, команды CLI, эксплуатация.

**Локальная проверка связки с Open WebUI без Exchange** — в
`tests/stand/README.md`: скрипт поднимает свой Open WebUI с моделью
`sofi-mail`, прогоняет через него конвейер и сносит за собой. Боевой `.env`
и рабочая база при этом не затрагиваются.

**Тесты** — `pytest -q` в корне проекта: 141 тест, сети не требуют, Exchange
и модель подменены заглушками.
