# sofi-mail

Чат с локальной LLM через электронную почту вместо веб-интерфейса.

За моделью закреплён отдельный почтовый ящик. Пользователь пишет туда письмо: тело письма
становится промптом, тема — названием сессии, приложенные документы уезжают в Open WebUI
и остаются доступными до конца переписки треда. Демон забирает письмо, генерирует ответ локальной
моделью и отправляет его ответом (Reply) на письмо пользователя: тема с префиксом `Re:`,
заголовки `In-Reply-To`, `References`, `Thread-Topic` и `Thread-Index`. По последним двум
Outlook и OWA кладут ответ в тот же разговор, а не в отдельную переписку. Ответ открывается
тегом `[Sofi]` — по нему переписка разбирается и человеком, и внешним парсером. Если
пользователь отвечает на письмо модели, вся переписка треда сохраняется и учитывается
при генерации. Новое письмо с новой темой начинает новую сессию.

```
EWS (polling) ──> разбор письма ──> сессия ──> модель ──> ответ письмом
Exchange          отсечение цитат   SQLite     sofi-mail  Re: + In-Reply-To
                  вложения          file_id    Open WebUI + Thread-Index
                  файл как есть     N потоков  (готовый MIME в EWS)
```

Служебные блоки `От:/Отправлено:/Кому:/Тема:` ставит сам Exchange — проект своих не добавляет
и использует их как границу цитаты. В `messages` ложится одна цепочка реплик, по одной строке
на письмо; переписка треда в реплику не переписывается, поэтому запрос растёт линейно
по числу писем, а не квадратично:

```
messages: user «текст запроса» │ assistant «[Sofi] текст ответа» │ user «…» │ assistant «…»
summaries: сводка ← заменяет реплики до неё, когда сессия переросла SESSION_MAX_CHARS
письмо:   Re: + In-Reply-To + Thread-Index → Outlook показывает ответ в том же разговоре
```

Модель настраивается не в проекте, а в Open WebUI: системный промпт, параметры генерации,
базы знаний и фильтры висят на модели `sofi-mail` в рабочем пространстве. Демон знает о ней
три вещи — адрес, ключ и `Model ID`; история переписки при этом остаётся в SQLite и в чаты
Open WebUI не уезжает.

Поставляется одним контейнером: демон, база сессий в томе, конфигурация — смонтированным `.env`.

## Сборка образа

```bash
cp .env.example .env      # заполнить перед первым запуском
docker compose build
```

Боевой образ собирается в два слоя. В первом стоят компиляторы и собираются зависимости,
во второй уезжает только готовый `venv`. Демон работает под непривилегированным
пользователем `sofi` (uid 1000), код принадлежит `root` и доступен процессу только на чтение.

### Сборка из Nexus

Всё, что тянется из сети, вынесено в build-args, поэтому в закрытом контуре базовый образ
и пакеты берутся из Sonatype Nexus, а не с `docker.io` и `pypi.org`. Значения читаются
из того же `.env`:

```dotenv
BASE_IMAGE=nexus.company.ru:8083/python:3.12-slim-bookworm
PIP_INDEX_URL=https://nexus.company.ru/repository/pypi-proxy/simple
PIP_TRUSTED_HOST=nexus.company.ru
DEBIAN_MIRROR=https://nexus.company.ru/repository/debian-proxy
APP_UID=1000                          # владелец каталога базы; важен при bind-mount
```

`DEBIAN_MIRROR` нужен только на слое сборки: `apt` там ставит `build-essential` и заголовки
`libxml2`/`libxslt` на случай, если прокси Nexus отдаст `lxml` исходником, а не колесом.
В боевом слое `apt` не вызывается вовсе.

`PIP_TRUSTED_HOST` отключает проверку сертификата **только для Nexus** и нужен, если его
сертификат выпущен внутренним УЦ, которого нет в базовом образе. Пусто — проверка обычная.

То же без compose:

```bash
docker build \
  --build-arg BASE_IMAGE=nexus.company.ru:8083/python:3.12-slim-bookworm \
  --build-arg PIP_INDEX_URL=https://nexus.company.ru/repository/pypi-proxy/simple \
  -t nexus.company.ru:8083/sofi-mail:1.0 .
```

### Публикация

```bash
docker login nexus.company.ru:8083
docker push nexus.company.ru:8083/sofi-mail:1.0
```

На целевом хосте образ не собирается, а забирается по тегу — в `.env` указывается
`SOFI_IMAGE=nexus.company.ru:8083/sofi-mail:1.0`, дальше `docker compose pull && docker compose up -d`.

## Настройка

Заполнить в `.env` шесть обязательных полей: `MAIL_ADDRESS`, `MAIL_PASSWORD`, `EWS_SERVER`,
`LLM_BASE_URL`, `LLM_API_KEY`, `ALLOWED_SENDERS`. Остальное — рабочие дефолты.

Файл `.env` в образ не попадает (он в `.dockerignore`), а монтируется в контейнер
на чтение: пароль служебной учётки не должен лежать ни в одном слое, потому что слои
уезжают в Nexus, где круг читателей шире круга допущенных к переписке.

### Почтовый ящик Exchange

Нужен **отдельный** ящик под модель, **в который не заходит человек**: демон забирает
непрочитанные письма, и открытый в Outlook ящик «съедал» бы их областью чтения. Альтернатива —
серверное правило, складывающее письма в отдельную папку, тогда её имя идёт в `EWS_FOLDER`.

Работаем через Exchange Web Services — тот же протокол, которым ходит Outlook, и единственный,
который в Exchange включён всегда:

```dotenv
MAIL_ADDRESS=sofi@so-ups.ru          # адрес ящика, от него уходят письма
MAIL_LOGIN=CORP\svc-llm              # логин служебной учётки, если он не равен адресу
MAIL_PASSWORD=<пароль служебной учётки>
EWS_SERVER=mail.company.ru           # пусто = autodiscover, но в закрытых сетях он часто недоступен
EWS_AUTH=ntlm                        # basic | ntlm | digest | oauth2; пусто = определить самому
EWS_ACCESS_TYPE=delegate             # impersonation, если учётка работает «от имени» ящика
```

`MAIL_ADDRESS` и `MAIL_LOGIN` — намеренно разные вещи: первое это **ящик** (объект Exchange,
под ним никто не входит), второе — **логин доменной учётной записи**, заведённой под программу.
Демон входит как `svc-llm`, а работает с ящиком `sofi@so-ups.ru`, поэтому учётной записи и нужны
права `Send As` и `FullAccess` на этот ящик. Свой почтовый ящик ей не нужен. Оставленный пустым
`MAIL_LOGIN` означает вход под самим ящиком — так тоже можно, но только если ящик не общий:
у общего ящика учётная запись AD отключена.

Здесь легко перепутать три разные сущности: **почтовый ящик** (`MAIL_ADDRESS`, адрес, с которого
приходят и уходят письма), **доменная учётная запись** (`MAIL_LOGIN`, от её имени демон входит
в Exchange) и **пользователь внутри контейнера** (`APP_UID`, владелец каталога с базой). Совпадать
они не обязаны и обычно не совпадают.

`oauth2` здесь не обязателен: поддерживаются `basic`, `ntlm`, `gssapi`, `sspi`, `digest` и `oauth2`,
пустое значение отдаёт выбор `exchangelib`. Где доступны оба пути (гибрид с Entra ID), **по умолчанию
берём `ntlm` + `delegate`** — не из консерватизма, а потому что эта пара открывает доступ ровно
к одному ящику, тогда как `full_access_as_app` без ограничения области — ко всем ящикам тенанта,
а `ApplicationImpersonation` без management scope — к любому ящику организации. Секрет приложения
не безопаснее пароля, если он лежит в том же `.env` и открывает на два порядка больше данных.

**Basic и NTLM отключены, оставлена современная аутентификация** (`EWS_AUTH=oauth2`) — нужна
регистрация приложения в Entra ID с правом `full_access_as_app` на EWS. Вариантов два, и выбор
между ними — по наличию `MAIL_PASSWORD`:

```dotenv
EWS_AUTH=oauth2
# регистрации приложения обязательно ограничить область одним ящиком
# (New-ApplicationAccessPolicy), иначе этот секрет открывает все ящики тенанта
EWS_CLIENT_ID=00000000-0000-0000-0000-000000000000
EWS_CLIENT_SECRET=...
EWS_TENANT_ID=...                    # пусто = тенант выберет Microsoft
MAIL_PASSWORD=                       # пусто: приложение работает от своего имени
EWS_ACCESS_TYPE=impersonation        # и тогда это обязательно
```

Пустой `MAIL_PASSWORD` — режим службы: пароль пользователя нигде не хранится, токен выдаётся
приложению, а ящик указывается заголовком impersonation (учётке нужно право
`ApplicationImpersonation`). Если пароль задан, приложение действует от имени пользователя, и
`EWS_ACCESS_TYPE=delegate` работает как обычно — но такой поток (ROPC) в тенантах часто запрещён
политикой. Несовместимую пару `oauth2` + `delegate` без пароля `check` отвергает на старте: Exchange
отвечает на неё `ErrorAccessDenied` при первом же чтении папки, и по этому ответу причину не угадать.

С `oauth2` контейнеру нужен доступ наружу до `login.microsoftonline.com:443` — токен выдаёт
Entra ID, и без правила на межсетевом экране подключение упрётся в него на первом же запросе.
При `ntlm` сервис не выходит за периметр вообще.

`EWS_AUTH=gssapi` (Kerberos) в этом образе не работает: `exchangelib` берёт его из
дополнительного пакета `pykerberos` (`exchangelib[kerberos]`), которого нет в
`requirements.txt`, а билет из кеша хоста контейнеру не виден — понадобился бы keytab
внутри него. В контейнере используются `ntlm` или `oauth2`.

Суть заявки администраторам Exchange — одна фраза: **служебной учётной записи выдать права
`FullAccess` и `Send As` на ящик модели**. Первое даёт читать письма, второе — отправлять от
адреса ящика; в Exchange это независимые права, и нужны оба. Остальное — отдельный ящик без
интерактивного входа, адрес точки входа EWS с включённым режимом аутентификации, корневой
сертификат внутреннего УЦ и потолок `EwsMaxConcurrency`, ограничивающий `WORKERS`.

```powershell
# права на ящик модели служебной учётной записи
Add-MailboxPermission -Identity sofi@so-ups.ru -User svc-llm -AccessRights FullAccess
Add-ADPermission     -Identity sofi@so-ups.ru -User svc-llm -ExtendedRights "Send As"

# потолок одновременных подключений EWS — им ограничен WORKERS
Get-ThrottlingPolicy | Select Name, EwsMaxConcurrency
```

### Сертификаты внутреннего УЦ

Сертификата корпоративного УЦ в базовом образе нет, поэтому проверка TLS до Exchange и до
сервера модели без него не пройдёт. Корневой сертификат кладётся в `certs/` **до сборки** —
каталог целиком копируется в образ по пути `/opt/sofi-mail/certs`:

```bash
cp corp-root.pem certs/
```

```dotenv
MAIL_CA_FILE=/opt/sofi-mail/certs/corp-root.pem
LLM_CA_FILE=/opt/sofi-mail/certs/corp-root.pem
```

Содержимое `certs/` не коммитится (`.gitignore`), в образ попадает только при сборке.
Если сертификат меняется чаще образа, его монтируют вместо копирования — добавив
в `docker-compose.yml` том `- /etc/pki/corp-root.pem:/opt/sofi-mail/certs/corp-root.pem:ro`.

### Модель

Модель живёт в Open WebUI: в рабочем пространстве под сервисной учётной записью заведена
модель `sofi-mail`, и на ней задано всё, что определяет ответ, — системный промпт, параметры
генерации (температура, потолок ответа, окно), базы знаний и фильтры. В проекте этих настроек
нет: одно место правки вместо двух, и правка не требует ни выкладки образа, ни доступа к
серверу. Демон отправляет только реплики переписки, а в теле запроса уходят ровно `model`
и `messages` — переданный параметр перекрыл бы настройку модели, и ответ разошёлся бы с тем,
что администратор видит в интерфейсе.

```dotenv
LLM_BASE_URL=https://sofi.cdu.so/api      # суффикс /api допишется, если забыть
LLM_CA_FILE=/opt/sofi-mail/certs/corp-root.pem
LLM_MODEL=sofi-mail                       # Model ID из Workspace -> Models
LLM_API_KEY=sk-...                        # ключ сервисной учётки, обязателен
LLM_WEB_URL=https://sofi.cdu.so           # пусто — из LLM_BASE_URL без /api
```

`LLM_WEB_URL` — единственная настройка модели, которую видит не демон, а пользователь: этот
адрес уходит в письмо тогда, когда документ почтой обработать нельзя и вопрос по нему нужно
задать руками (см. [вложения](#вложения)).

Что настраивается в Open WebUI один раз:

1. **Сервисная учётная запись.** Под ней заводится модель и от её имени ходит демон;
   личная учётка администратора не подходит — уйдёт вместе с человеком.
2. **Workspace → Models → New model.** Базовая модель — та, что отдаёт сервер инференса.
   В `Model ID` кладётся `sofi-mail`, это же значение идёт в `LLM_MODEL`.
3. **System prompt** — правила ответа: язык письма, без markdown-разметки (ответ читают в
   почтовом клиенте как обычный текст), без приветствия и подписи (подпись подставляет демон),
   учитывать историю сессии как один непрерывный диалог.
4. **Advanced params** — температура, потолок ответа и окно контекста.
5. **Knowledge и Filters** — базы знаний и фильтры, если они нужны.
6. **Settings → Account → API keys** — ключ сервисной учётки в `LLM_API_KEY`. Он же
   определяет, чью модель видит демон: под другой учёткой `sofi-mail` в списке не появится.

Проверка доступности из контейнера — тем же образом, что и работает демон, то есть с его
сетевым доступом и его сертификатами:

```bash
docker compose run --rm sofi-mail check
```

Адрес обязан быть `https`: в запросе уходит полный текст письма и вся история сессии, и по
`http` это открытый текст в корпоративной сети — демон с `http`-адресом не стартует. Если TLS
поднять нельзя, а сегмент изолирован, отказ оформляется явно: `LLM_ALLOW_INSECURE=true`.

**Адрес заканчивается на `/api`, а не на `/v1`.** Генерация в Open WebUI идёт по
`POST /api/chat/completions`; путь `/api/v1/...` — это его внутренний REST (чаты, знания,
файлы), генерации там нет. Хвост `/v1` остался в конфигурациях со времён прямого обращения
к vLLM, поэтому `check` отвергает такой адрес на старте, а не оставляет ловить 404 в логах.

`LLM_MODEL` сверяется со списком моделей строго, точным равенством: подстановка имени базовой
модели увела бы запрос мимо `sofi-mail` — ответ пришёл бы, но без промпта, знаний и фильтров,
и заметить это можно далеко не сразу. `check` при несовпадении печатает доступные модели.

Дефолта у `LLM_BASE_URL` намеренно нет: молчаливое обращение к себе же выглядело бы как
«сервер недоступен», и причину искали бы на чужой машине вместо своего `.env`.

**История переписки остаётся в SQLite, чаты в Open WebUI не создаются** (`/api/v1/chats/new`).
Дело не в экономии запросов: у базы есть срок хранения (`RETENTION_DAYS`), удаление по
требованию (`forget`) и маскирование в логах, а чаты, заведённые под общей сервисной учётной
записью, сложились бы в один общий журнал переписки всех пользователей, доступный каждому,
у кого есть её ключ.

**Контекст сессии не обрезается.** История читается из базы целиком
(`MAX_HISTORY_MESSAGES=0`), письмо входит в запрос целиком (`MAX_PROMPT_CHARS=0`). Молчаливая
потеря реплик неотличима для пользователя от новой сессии: модель отвечает так, будто
предыдущих писем не было. Держать всю историю позволяет линейный рост: в реплику пишется
только новый текст письма. Цитату отсекают три признака — служебный блок, который поставил
Exchange, метка `[Sofi]` в первой строке нашего прошлого ответа и подпись под ним
(`strip_own_replies`).

Окно контекста задано на модели и клиенту не видно, поэтому размер запроса сверяется
с грубым порогом `MAX_CONTEXT_CHARS` (символы, история + текущее письмо). Порог ничего
не режет: превышение пишет в лог функция `llm.fit_context`, а запрос уходит целиком.
Ориентир для порога — окно в токенах, умноженное на 3, с запасом на ответ и на то,
что подмешают знания и фильтры. Объём самой сессии держит свёртка в сводку.

### Суммаризация сессии

Переписка треда растёт без предела, окно модели конечно. Когда сессия вместе с текущим
письмом переваливает за `SESSION_MAX_CHARS`, реплики, предшествующие этому письму,
заменяются одной сводкой (`src/summarizer.py`). Ответ на письмо собирается уже по сводке;
само письмо в неё не входит.

Сводку пишет та же модель. В запросе на суммаризацию переписка идёт стенограммой,
где у каждой реплики проставлен автор и адресат:

```
Пользователь (ivan@company.ru) → Sofi:
<текст письма>

Sofi → Пользователь (ivan@company.ru):
<текст ответа>
```

Требования к сводке заданы в промпте: назвать автора каждой мысли, сохранить вопросы,
ответы, числа, решения и открытые вопросы, время писем не указывать, ничего не отвечать
от себя. Целевую длину задаёт `SUMMARY_COMPRESSION_RATIO` — доля от объёма свёрнутой
переписки (`0.2` — сводка впятеро короче). Модель держит её приблизительно, поэтому
это ориентир, а не жёсткий предел; нижняя граница защищает короткую переписку,
верхняя (половина `SESSION_MAX_CHARS`) оставляет запас на новые письма.

Свернуть переписку можно и письмом: `/summary` в первой строке либо просьба словами —
нужны и действие, и предмет («суммаризируй нашу переписку», «подведи итог обсуждения
в этой сессии»). Ответом на такое письмо служит сама сводка, и после него в контексте
сессии остаётся только она. Письмо с вложением по этой ветке не идёт: «подведи итог»
при документе относится к документу. Длинное письмо просьбой не считается
(`MAX_REQUEST_CHARS`) — цена ложного срабатывания выше цены нераспознанной просьбы.

Свёрнутые письма остаются в базе и в цепочке у пользователя в почте, но в запрос
не попадают: `storage.get_history` отбирает реплики по границе сводки (`covers_upto`),
цитату снимает `email_parser`, а шапка сводки (`llm.SUMMARY_PREFIX`) прямо говорит модели
опираться на сводку, а не на цитату. Сами письма остаются якорями треда в `messages` —
по ним ответ пользователя находит свою сессию. Команда `python -m src.cli history <id>`
показывает переписку целиком и помечает свёрнутое.

Сбой суммаризации ответ не отменяет: при автоматической свёртке запрос уходит полным
контекстом, а причина остаётся в логе. По прямой просьбе пользователь получает письмо
с причиной, контекст сессии не меняется.

Open WebUI и сервер инференса стоят отдельными машинами, поэтому в `compose` их нет:
контейнер ходит к ним по сети как обычный клиент.

### Вложения

К письму можно приложить документы: PDF, docx, pptx, xlsx, doc, xls, ppt, csv, txt, md, html,
а также картинки. Путь документа такой:

```
письмо ──> POST /api/v1/files/ ──> GET …/process/status ──> files:[{id}] в запросе к модели
           (оригинал файла)        (ждём индексации)        (разбор и поиск — на стороне owui)
```

**Разбирает документ Open WebUI, а не сервис.** В хранилище уезжает оригинал файла, обратно
приходит `file_id`; извлечения текста в проекте нет. Так набор форматов, распознавание текста
и качество разбора обновляются на стороне owui — без пересборки нашего образа и без второго,
расходящегося с сервером, набора парсеров. Прежде текст извлекался здесь библиотеками
`unstructured` и `pdfminer.six`: около гигабайта в образ ради результата, который сервер и так
умеет получить сам.

**Режим подачи документа сервис не выбирает.** Ссылка на файл уходит в запрос как
`{"type": "file", "id": …}`, без поля `context`: фокусированный поиск по документу Open WebUI
включает сам. Подачу целиком (`full_context`) включает инструмент, лежащий в
`src/tools/full_context_tool.py`, — он ставится в owui через **Рабочее пространство →
Инструменты → создать** и включается у модели, которой отвечает sofi-mail. Инструмент видит
вложения запроса и отдаёт модели их содержимое целиком, когда вопрос требует документа
в целом: пересказ, перечисление всех упоминаний, проверка отсутствия чего-либо в документе.
Настройка *Full Context Mode* в интерфейсе owui эту задачу не решает — она включается вручную
на каждый чат и до запросов, приходящих по API, не доходит.

Пределы инструмента (`Valves` в его настройках):

| Настройка | По умолчанию | Что держит |
| --- | --- | --- |
| `max_chars` | 200 000 | суммарный объём документов, уходящих в модель |
| `max_file_chars` | 100 000 | предел на один документ: первый файл не занимает весь бюджет |
| `include_names` | true | подписывать документы именами в тексте ответа |

Документы, не поместившиеся в предел, названы в хвосте ответа поимённо — иначе ответ по половине
пакета выглядел бы как ответ по всему пакету.

**На стороне sofi-mail от вложения осталось две проверки**, обе дешёвые и обе о том, что
до сервера доезжать не должно: вес файла (`ATTACHMENT_MAX_MB`) и расширение. Пустой файл
тоже отсекается — сервер проиндексировал бы его пустотой, и ответ по нему собрался бы из ничего.
Архивы не принимаются: внутри лежит ещё один слой вложений, и ответ про него отличается
от ответа про формат. Картинки из подписи (логотипы, вставленные в тело скриншоты) вложениями
не считаются и в Open WebUI не уезжают.

В текст запроса перед вопросом встаёт описание документа — без него вопрос «что в акте»
не связывается ни с одним из приложенных файлов:

```
К письму приложен документ «регламент.pdf» (412 КБ); его содержимое доступно поиском.
```

Отказ по файлу ответ не отменяет: пользователь получает ответ по остальному письму
и примечание о том, что приложить не удалось. Письмо, в котором кроме такого файла ничего
не было, до модели не доходит вовсе — в ответ уходит только объяснение.

```dotenv
ATTACHMENTS_ENABLED=true             # false — вложения игнорируются с примечанием в ответе
ATTACHMENT_MAX_MB=20                 # потолок на один файл
ATTACHMENT_MAX_COUNT=5               # файлов из одного письма
ATTACHMENT_MAX_SESSION_FILES=10      # файлов треда в одном запросе к модели
ATTACHMENT_PROCESS_TIMEOUT_SEC=120   # сколько ждать индексации файла в owui
ATTACHMENT_RETENTION_DAYS=30         # срок жизни файла в Open WebUI; 0 — не удалять
```

**`file_id` хранится в базе, в таблице `session_files`.** Это нужно для follow-up писем: второе
письмо треда («а что в разделе 7?») спрашивает про тот же документ, а не грузит его копию —
иначе каждое письмо удваивало бы то, что сервис оставил в общем хранилище. Там же лежит вес
файла (`bytes`): содержимое документа у нас не хранится, и описать документ в следующем письме
треда больше нечем. Колонка `bytes` появилась с переходом на серверный разбор, поэтому базы,
заведённые раньше, дополняются на старте: демон сверяет состав колонок и доставляет недостающие
(`_ADDED_COLUMNS` в `src/storage.py`). Проверка идёт при каждом запуске, ничего не переносит
и не переписывает; у файлов, записанных до перехода, вес остаётся нулевым — в описании на его
месте стоит «объём неизвестен». Прежние колонки `pages`, `chars`, `full_context` и `outline`
из схемы убраны; в старых базах они остаются на месте и вставке не мешают.

**Файлы удаляются по своему сроку** — `DELETE /api/v1/files/{id}` через 30 дней. Срок отдельный
от `RETENTION_DAYS` намеренно: в Open WebUI документы лежат под общей сервисной учётной записью,
то есть в более широком доступе, чем база демона, и держать их дольше переписки незачем. Уборка
идёт в самом демоне раз в сутки; `purge` и `forget` снимают файлы своих сессий до удаления
переписки — каскад унёс бы строки `session_files`, и удалять в Open WebUI стало бы нечего.

```bash
docker compose run --rm sofi-mail files                 # что лежит в Open WebUI и от каких сессий
docker compose run --rm sofi-mail purge-files --days 7  # разовая чистка
```

**Что уходит наружу.** В общее хранилище сервисной учётной записи попадает оригинал файла —
со всеми макросами, скрытыми правками и метаданными автора. Это плата за серверный разбор:
раньше туда уезжал только извлечённый текст. Срок хранения там свой
(`ATTACHMENT_RETENTION_DAYS`), и укоротить его отдельно от переписки остаётся возможным.

## Запуск

```bash
docker compose run --rm sofi-mail check            # диагностика: конфиг, база, сервер модели, ящик
docker compose run --rm sofi-mail serve --dry-run -v  # первый запуск: ответы печатаются, письма не уходят
docker compose up -d                               # рабочий режим
docker compose logs -f
```

`docker compose up -d` поднимает демона в рабочем режиме; всё остальное запускается
через `run --rm` — разовым контейнером на том же томе с базой.

Контейнер настроен на минимум прав: корневая файловая система только для чтения, все
capabilities сброшены, `no-new-privileges`, запись возможна лишь в том с базой и в tmpfs
`/tmp`. Демон при подключении сам приводит каталог базы к `0700`, а файл — к `0600`.

**Остановка.** `docker compose stop` шлёт SIGTERM, демон дорабатывает текущий цикл и выходит
штатно — обычно за секунду. Если в этот момент генерируется ответ, остановка ждёт модель;
поэтому `stop_grace_period` взят с запасом над `LLM_TIMEOUT_SEC` (330 с против 300 с), чтобы
штатная остановка не рвала генерацию на половине. Если контейнер остановлен аварийно, письма,
зависшие в обработке, помечаются как `error` при следующем старте и возвращаются в очередь
командой `retry`.

### Параллельная обработка

По умолчанию `WORKERS=1` — письма обрабатываются по одному, чего достаточно для личного ящика.
`WORKERS=4` (или флаг `-w 4`) обрабатывает письма пулом потоков.

Второй экземпляр демона на тот же ящик поднимать нельзя: оба заберут одни и те же
непрочитанные письма и ответят дважды. Масштабирование — через `WORKERS`, а не через реплики.

## Команды

Точка входа образа — сам CLI, поэтому команда идёт аргументом контейнера:
`docker compose run --rm sofi-mail <команда>`.

| Команда | Назначение |
|---|---|
| `serve` | демон: опрашивает ящик каждые `POLL_INTERVAL_SEC` и отвечает на письма; `-w N` — потоков |
| `once` | один проход по непрочитанным — основной инструмент отладки |
| `check` | проверка конфига, базы, сервера модели и доступа к ящику Exchange |
| `ask "текст" [-s ID]` | спросить модель из терминала, без почты |
| `sessions` | список сессий: id, число реплик, собеседник, тема |
| `history ID [--raw]` | переписка сессии; `--raw` — тело до отсечения цитаты (нужен `STORE_RAW_BODY=true`) |
| `send-test` | отправить тестовое письмо самому себе |
| `retry` | вернуть письма со статусом `error` в очередь |
| `purge [--days N]` | удалить переписку старше срока хранения (демон делает это и сам, раз в сутки) |
| `forget --session N \| --address A` | удалить переписку по требованию: сессию или все сессии адреса |
| `files` | документы, загруженные в Open WebUI, и от каких они сессий |
| `purge-files [--days N]` | удалить из Open WebUI документы старше срока (демон делает это и сам) |
| `ingest-eml FILE [--show-parsed]` | прогнать сохранённое письмо через пайплайн без почты |

Флаг `-v` включает DEBUG-лог и принимается в любой позиции.

База открыта в режиме WAL, поэтому `sessions` и `history` читаются на работающем демоне,
без его остановки. `ingest-eml` требует файла внутри контейнера — его подкидывают монтированием:
`docker compose run --rm -v $PWD/письмо.eml:/tmp/m.eml sofi-mail ingest-eml /tmp/m.eml`.

## Эксплуатация

**Обновление.** Собрать и опубликовать новый тег, на хосте — `docker compose pull &&
docker compose up -d`. Том с базой переживает пересоздание контейнера, недостающие таблицы
`init_db` создаёт при старте. Автоматической миграции схемы в коде нет: если новая версия
меняет структуру существующих таблиц, `ALTER TABLE` выполняется отдельно, до подъёма
контейнера. Откат — прежним тегом в `SOFI_IMAGE`.

**Бэкап базы.** В базе лежит переписка целиком, поэтому копия — такие же ПДн, как оригинал,
и хранить её нужно соответственно. Снимок снимается штатным механизмом SQLite прямо
на работающем демоне; просто скопировать файл нельзя — рядом лежит незакоммиченный WAL:

```bash
mkdir -p backup && sudo chown 1000:1000 backup    # писать будет пользователь образа
docker compose run --rm -v "$PWD/backup:/backup" --entrypoint python sofi-mail -c \
  "import sqlite3; s=sqlite3.connect('/opt/sofi-mail/data/sessions.db'); \
d=sqlite3.connect('/backup/sessions.db'); s.backup(d); d.close(); s.close()"
mv backup/sessions.db backup/sessions-$(date +%F).db
```

**Логи.** Демон пишет в stdout, дальше их забирает драйвер журналирования Docker (ротация
10 МБ × 5 задана в `compose`). Адреса в логе маскируются, темы писем не пишутся вовсе;
`LOG_PII=true` включается только на время разбора конкретной проблемы, потому что журнал
уезжает в систему сбора логов, где читателей больше, чем допущенных к переписке.

## Как устроено

| Модуль | Ответственность |
|---|---|
| `src/config.py` | единственная точка чтения `.env` |
| `src/storage.py` | SQLite: сессии, реплики, сводки, журнал обработанных писем |
| `src/email_parser.py` | разбор MIME, кодировки, отсечение цитат и прошлых ответов, фильтры петель |
| `src/transport.py` | контракт почты: пять операций, которыми пользуется пайплайн |
| `src/ews_client.py` | приём и отправка через Exchange Web Services |
| `src/reply_builder.py` | сборка ответа: метка `[Sofi]`, заголовки треда и разговора (MIME, который EWS отдаёт как есть) |
| `src/llm.py` | сборка контекста, бюджет запроса, отсечение рассуждений |
| `src/summarizer.py` | свёртка переписки в сводку: предел сессии, разбор просьбы, запрос на суммаризацию |
| `src/llm_backend.py` | обращение к Open WebUI: адрес, ключ, TLS, сверка Model ID |
| `src/attachments.py` | проверка вложений: вес, формат, mime-тип, имя для хранилища |
| `src/owui_files.py` | файлы в Open WebUI: загрузка, готовность, удаление, срок хранения |
| `src/redact.py` | маскирование адресов и тем писем в логах |
| `src/pipeline.py` | оркестрация: письмо → сессия → ответ → письмо, пул воркеров |
| `src/cli.py` | Typer, единая точка входа |

Модули самостоятельно не запускаются: `once` и `serve` вызывают один и тот же `process_email`,
поэтому отлаженное вручную поведение совпадает с поведением демона.

| Файл сборки | Назначение |
|---|---|
| `Dockerfile` | три стадии: сборка зависимостей, тесты (`--target test`), боевой образ |
| `docker-compose.yml` | выкладка: том с базой, ограничения прав, ротация логов |
| `.dockerignore` | не пускает в контекст сборки `.env`, `data/` и историю git |
| `certs/` | корневые сертификаты внутреннего УЦ, копируются в образ |
