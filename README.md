# llm-email-chat

Чат с локальной LLM через электронную почту вместо веб-интерфейса.

За моделью закреплён отдельный почтовый ящик. Пользователь пишет туда письмо: тело письма
становится промптом, тема — названием сессии. Демон забирает письмо, генерирует ответ локальной
моделью в Ollama и отправляет его на адрес отправителя. Если пользователь отвечает (Reply)
на письмо модели, вся переписка треда сохраняется и учитывается при генерации. Новое письмо
с новой темой начинает новую сессию.

Работает и на публичной почте (Gmail, Яндекс, Mail.ru), и на корпоративном Microsoft Exchange —
транспорт выбирается одной переменной `MAIL_TRANSPORT`.

```
транспорт (polling) ──> разбор письма ──> сессия ──> Ollama ──> ответ письмом
IMAP+SMTP или EWS       отсечение цитат   SQLite     qwen3:4b   Re: + In-Reply-To
                                                     N потоков
```

## Установка

```bash
uv venv && uv pip install -r requirements.txt
uv pip install -r requirements-ews.txt     # только для MAIL_TRANSPORT=ews
cp .env.example .env
```

Заполнить в `.env` три обязательных поля: `MAIL_ADDRESS`, `MAIL_PASSWORD`, `ALLOWED_SENDERS`.
Остальное — рабочие дефолты.

### Почтовый ящик

Нужен **отдельный** ящик под модель и **пароль приложения**, а не пароль аккаунта.

| Провайдер | Как получить пароль | IMAP | SMTP |
|---|---|---|---|
| Gmail | включить 2FA → [Пароли приложений](https://myaccount.google.com/apppasswords) | `imap.gmail.com:993` | `smtp.gmail.com:587`, STARTTLS |
| Яндекс | включить IMAP в настройках почты → пароль приложения | `imap.yandex.ru:993` | `smtp.yandex.ru:465`, `SMTP_TLS=ssl` |
| Mail.ru | «Пароль для внешних приложений» | `imap.mail.ru:993` | `smtp.mail.ru:465`, `SMTP_TLS=ssl` |

`IMAP_FOLDER` оставить `INBOX`. Читать `[Gmail]/All Mail` нельзя: там лежат и наши собственные
отправленные письма, это мгновенная петля.

### Microsoft Exchange

Два варианта — по тому, что включено у администраторов.

**IMAP и SMTP включены** (`MAIL_TRANSPORT=imap`) — обычная схема, отличий от публичной почты три:

```dotenv
MAIL_ADDRESS=llm@company.ru          # адрес ящика, от него уходят письма
MAIL_LOGIN=CORP\svc-llm              # логин служебной учётки, если он не равен адресу
IMAP_HOST=mail.company.ru
IMAP_PORT=143
IMAP_STARTTLS=true                   # внутри периметра 993 часто закрыт
SMTP_HOST=mail.company.ru
SMTP_PORT=25
SMTP_TLS=none                        # релей на 25-м порту обычно без шифрования
SMTP_AUTH=false                      # и без авторизации: login() упал бы с SMTPNotSupportedError
```

**IMAP выключен или оставлена только NTLM/Kerberos-аутентификация** (`MAIL_TRANSPORT=ews`) —
работаем через Exchange Web Services, тот же протокол, которым ходит Outlook:

```dotenv
MAIL_TRANSPORT=ews
MAIL_ADDRESS=llm@company.ru
MAIL_LOGIN=CORP\svc-llm
EWS_SERVER=mail.company.ru           # пусто = autodiscover, но в закрытых сетях он часто недоступен
EWS_AUTH=ntlm                        # gssapi — по билету Kerberos, пароль тогда не нужен
EWS_ACCESS_TYPE=delegate             # impersonation, если учётка работает «от имени» ящика
```

**Basic и NTLM отключены, оставлена современная аутентификация** (`EWS_AUTH=oauth2`) — нужна
регистрация приложения в Entra ID с правом `full_access_as_app` на EWS. Вариантов два, и выбор
между ними — по наличию `MAIL_PASSWORD`:

```dotenv
MAIL_TRANSPORT=ews
EWS_AUTH=oauth2
EWS_CLIENT_ID=00000000-0000-0000-0000-000000000000
EWS_CLIENT_SECRET=...
EWS_TENANT_ID=...                    # пусто = тенант выберет Microsoft
MAIL_PASSWORD=                       # пусто: приложение работает от своего имени
EWS_ACCESS_TYPE=impersonation        # и тогда это обязательно
```

Пустой `MAIL_PASSWORD` — режим службы: пароль пользователя нигде не хранится, токен выдаётся
приложению, а ящик указывается заголовком impersonation (учётке нужно право
`ApplicationImpersonation`). Если пароль задан, приложение действует от имени пользователя, и
`EWS_ACCESS_TYPE=delegate` работает как обычно — но такой поток (ROPC) в тенантах часто запрещён
политикой. Несовместимую пару `oauth2` + `delegate` без пароля `check` отвергает на старте: Exchange
отвечает на неё `ErrorAccessDenied` при первом же чтении папки, и по этому ответу причину не угадать.

Что спросить у администраторов: запущена ли служба `MSExchangeIMAP4` (в Exchange 2013+ по
умолчанию нет); какие порты и режим TLS открыты; разрешена ли Basic-аутентификация, а если нет —
заведут ли регистрацию приложения для OAuth2; выдадут ли служебной учётке право **Send As** на ящик —
без него Exchange отклонит письмо с чужим `From`.

Ещё три момента, специфичные для корпоративной среды:

- **Сертификат внутреннего УЦ.** Проверка сертификата включена (`MAIL_TLS_VERIFY=true`). Если
  корневого сертификата нет в системном хранилище — указать файл в `MAIL_CA_FILE`. Отключать
  проверку (`MAIL_TLS_VERIFY=false`) стоит только на время отладки.
- **Ящик не должен читать человек.** Демон забирает непрочитанные письма; если кто-то откроет
  общий ящик в Outlook, письмо станет прочитанным в области чтения и до модели не дойдёт.
  Нужен ящик, в который никто не заходит, либо серверное правило, складывающее письма
  в отдельную папку — её имя в `IMAP_FOLDER` или `EWS_FOLDER`.
- **Формат письма.** Outlook, настроенный на RTF, упаковывает текст в `winmail.dat`, и прочитать
  вопрос невозможно. Такому отправителю приходит ответ с просьбой переключить формат на HTML
  или обычный текст; правильнее выключить RTF политикой на стороне Exchange.

`THREAD_BY_SUBJECT=false` в компании почти обязателен: темы вроде «Вопрос» повторяются
постоянно, и фоллбэк по теме склеит переписки разных людей в одну сессию.

## Запуск

```bash
python -m src.cli check                    # диагностика: конфиг, база, Ollama, почта
python -m src.cli serve --dry-run -v       # первый запуск: ответы печатаются, письма не уходят
python -m src.cli serve                    # рабочий режим
python -m src.cli serve -w 4               # сервис на компанию: 4 письма одновременно
```

### Параллельная обработка

По умолчанию `WORKERS=1` — письма обрабатываются по одному, чего достаточно для личного ящика.
Для сервиса на отдел или компанию это очередь: узкое место — генерация, и один ответ `qwen3:4b`
занимает порядка полутора минут, так что второй сотрудник всё это время ждёт.

`WORKERS=4` (или флаг `-w 4`) обрабатывает письма пулом потоков. Три вещи, которые важно понимать:

- **Ollama тоже должна быть готова к параллелизму.** Она держит собственную очередь: если
  `OLLAMA_NUM_PARALLEL` меньше `WORKERS`, письма выстроятся уже в неё, и клиентские потоки
  ничего не ускорят. Свежие версии подбирают этот параметр сами по доступной памяти — на машине
  разработки три запроса к `qwen3:4b` заняли 10 с вместо 20 с последовательных, то есть
  параллелизм работал без настройки. Но на сервере это стоит проверить и задать явно: память
  под KV-кэш тратится на каждый параллельный запрос отдельно. `check` печатает напоминание,
  когда `WORKERS > 1`.
- **Реплики одной сессии всё равно обрабатываются по очереди.** Иначе два письма одного треда
  прочитали бы одну и ту же историю, и каждый ответ был бы построен без учёта второго вопроса.
  Параллельно идут разные сессии, а не разные письма одного разговора.
- **Отметка «обработано» ставится в главном потоке**, после того как пул отработал: ни
  IMAP-соединение, ни сессия EWS не рассчитаны на команды из нескольких потоков одновременно.

Отправка на каждое письмо открывает своё соединение, поэтому она потокобезопасна на обоих
транспортах.

## Команды

| Команда | Назначение |
|---|---|
| `serve` | демон: опрашивает ящик каждые `POLL_INTERVAL_SEC` и отвечает на письма; `-w N` — потоков |
| `once` | один проход по непрочитанным — основной инструмент отладки |
| `check` | проверка конфига, базы, Ollama и почты (активного транспорта) |
| `ask "текст" [-s ID]` | спросить модель из терминала, без почты |
| `sessions` | список сессий: id, число реплик, собеседник, тема |
| `history ID [--raw]` | переписка сессии; `--raw` показывает тело до отсечения цитаты |
| `send-test` | отправить тестовое письмо самому себе |
| `retry` | вернуть письма со статусом `error` в очередь |
| `ingest-eml FILE [--show-parsed]` | прогнать сохранённое письмо через пайплайн без почты |

Флаг `-v` включает DEBUG-лог и принимается в любой позиции: и `cli -v serve`, и `cli serve -v`.

## Если что-то не работает

**`не удалось отправить ответ: timed out`** — закрыт исходящий SMTP-порт. Пароль тут не при чём:
при неверном пароле сервер отвечает ошибкой авторизации, а не молчит. Чаще всего виноват
**включённый VPN**, реже — провайдер или корпоративная сеть: порты 25/465/587 массово режут
как антиспам-меру. Проверка одной командой:

```bash
nc -vz smtp.yandex.ru 465     # соединение либо есть, либо таймаут
```

Показательно, что IMAP при этом работает: 993 не блокируют почти никогда, поэтому «почту читает,
а отправить не может» — типичная картина именно этой проблемы. `check` на таймауте SMTP печатает
подсказку вместо голого текста ошибки.

**`сбой цикла (command: UID => socket error: EOF)`** — сервер закрыл простаивающее IMAP-соединение,
пока модель генерировала ответ. Это штатное поведение почтовых серверов, а не сбой: клиент
переподключается и повторяет команду (UID-ы стабильны между сессиями), письмо не теряется.
В логе останется `IMAP-соединение разорвано ... переподключаюсь` на уровне WARNING.

## Как устроено

| Модуль | Ответственность |
|---|---|
| `src/config.py` | единственная точка чтения `.env` |
| `src/storage.py` | SQLite: сессии, реплики, журнал обработанных писем |
| `src/email_parser.py` | разбор MIME, кодировки, отсечение цитат, фильтры петель |
| `src/transport.py` | контракт транспорта и выбор реализации по `MAIL_TRANSPORT` |
| `src/imap_client.py` | приём писем по IMAP (UID + `BODY.PEEK`) |
| `src/smtp_client.py` | сборка ответа с заголовками треда и отправка по SMTP |
| `src/ews_client.py` | приём и отправка через Exchange Web Services |
| `src/tls.py` | TLS-контекст для всех трёх клиентов |
| `src/llm.py` | ChatOllama, сборка контекста, бюджет окна |
| `src/pipeline.py` | оркестрация: письмо → сессия → ответ → письмо, пул воркеров |
| `src/cli.py` | Typer, единая точка входа |

Модули самостоятельно не запускаются: `once` и `serve` вызывают один и тот же `process_email`,
поэтому отлаженное вручную поведение совпадает с поведением демона.

### Решения, которые стоит знать при доработке

**Ровно один ответ на письмо.** Идемпотентность держится на таблице `processed`, а не на
IMAP-флаге `\Seen`: заявка на письмо ставится *до* вызова модели, поэтому падение между
генерацией и отправкой не приводит к повторному ответу после перезапуска. Ответ сохраняется
в историю строго *после* успешной отправки.

**Транспорт — пять операций.** `pipeline.py` не знает о протоколе: он умеет только забрать
непрочитанные, отметить обработанным, вернуть письмо в очередь, отправить ответ и переподключиться
(`src/transport.py`). Поэтому поддержка Exchange — отдельный модуль, а не ветвления по коду.

Ответное письмо оба транспорта собирают одним и тем же `smtp_client.build_reply`, и EWS отправляет
готовый MIME (`mime_content`). Это не мелочь: если собирать письмо средствами EWS, `Message-ID`
присвоит сервер, а на нём держится сопоставление будущего Reply с сессией — его пришлось бы
вычитывать из «Отправленных», и до тех пор тред опознавался бы только фоллбэком по теме.

**TLS по умолчанию не проверяется — в stdlib.** И `imaplib`, и `smtplib` при `context=None` берут
`ssl._create_stdlib_context()`, у которого `verify_mode=CERT_NONE` и `check_hostname=False`.
Поэтому `src/tls.py` всегда передаёт контекст явно: это не перестраховка, а исправление
небезопасного поведения по умолчанию.

**Сопоставление тредов** идёт по `In-Reply-To` → `References` → (если `THREAD_BY_SUBJECT=true`)
отправитель + нормализованная тема. Message-ID наших исходящих писем генерируется до отправки
и кладётся в базу — именно по нему находит свою сессию будущий Reply.

Фоллбэк по теме прощает клиентов, вырезающих заголовки, но новое письмо с точно такой же темой
продолжит старую сессию. Нужно строгое «Reply = продолжение, новое письмо = новая сессия» —
поставить `THREAD_BY_SUBJECT=false`.

**Отсечение цитаты.** В подпись каждого исходящего письма кладётся маркер `[llm-email-chat]`,
и входящее режется по нему — формат наш, поэтому это надёжнее любой эвристики. Дальше идут
регулярки под Gmail (обе локали), Яндекс, Mail.ru и Outlook. Если после отсечения не осталось
текста, берётся неочищенное тело: пустой промпт выглядит как «модель тупит», хотя это баг разбора.

**qwen3:4b и thinking.** Рассуждения у этой модели не отключаются ни `think: false`, ни
`/no_think`. Нативный API Ollama отдаёт их отдельным полем, в `content` приходит чистый ответ,
поэтому `OLLAMA_NUM_PREDICT` обязан покрывать рассуждения (~2–3.5K токенов) **и** сам ответ.
`keep_alive=-1` держит модель в памяти между письмами.

**Контекст.** История обрезается с самых старых реплик под окно
`OLLAMA_NUM_CTX − OLLAMA_NUM_PREDICT`. Системный промпт (`prompts/system.txt`) и текущее письмо
не выбрасываются никогда. Для длинных переписок поднять `OLLAMA_NUM_CTX` до 32768 — qwen3:4b
держит это нативно, ценой RAM под KV-кэш.

**Безопасность.** Отвечаем только адресам из `ALLOWED_SENDERS` (запись вида `@company.ru`
разрешает домен целиком); посторонним — молча, без ответа, иначе ответ подтвердит спамеру, что
ящик живой. Отсекаются автоответчики (`Auto-Submitted`, `Precedence`, `List-Id`, `no-reply@`),
отчёты о доставке и письма с нашим собственным заголовком `X-LLM-Email-Chat`. Тело письма
попадает в промпт как есть — это недоверенный ввод, и whitelist здесь основная мера защиты.
Вложения не читаются вообще.

## Тестирование

```bash
pytest tests/ -q                                          # парсер, сессии, пайплайн — без сети
python -m src.cli ingest-eml tests/fixtures/gmail_ru_reply.eml --show-parsed
```

Фикстуры в `tests/fixtures/` покрывают Gmail с русской локалью, Яндекс, Outlook, HTML-only
письмо, windows-1251, заявленный-но-ложный charset, письмо без Message-ID, автоответчик
и письмо Outlook в формате RTF (`winmail.dat`). Свои письма для отладки берутся так:
Gmail → «Показать оригинал» → «Скачать сообщение»; Outlook → «Сохранить как» → `.eml`.

Сеть не нужна нигде: EWS-транспорт проверяется на заглушках `exchangelib`
(`tests/test_ews_client.py` пропускается, если пакет не установлен), параллельная обработка —
на замедленной генерации (`tests/test_concurrency.py`: письма действительно идут одновременно,
реплики одной сессии — по очереди, одна тема не порождает две сессии).

Проверка исходящих писем без реальной отправки:

```bash
python -m aiosmtpd -n -l localhost:1025          # печатает письмо целиком
SMTP_HOST=localhost SMTP_PORT=1025 SMTP_TLS=none SMTP_AUTH=false python -m src.cli once
```

Сценарий полной проверки: письмо → ответ → Reply на него (модель должна опираться на историю) →
новое письмо с другой темой (контекст не должен протечь) → `sessions` и `history`. Для сервисного
режима добавить проверку параллелизма: отправить 3–4 письма с разных адресов сразу и убедиться
по логу, что они обрабатываются одновременно, а не по очереди.
